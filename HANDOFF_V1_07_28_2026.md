## 2. HARD PLATFORM CONSTRAINT - DO NOT RE-LITIGATE

**Galaxy Watch 7 (SM-L310) runs Wear OS 6** (Android 16 / SDK 36 / One UI Watch 8.0).
Verified via `adb shell getprop`.

Wear OS 6 **blocks programmatic watch faces**. A Kotlin `WatchFaceService` installs and
registers correctly but is refused by the system. Confirmed in this device's own logcat:

```
WearServices: [WFInfoResolver] Blocked watch face
  WatchFaceId[com.reddoor3.forexdial, com.reddoor3.forexdial.wear.ForexDialWatchFaceService]
```

**Watch Face Format XML is the only option.** The dead Kotlin renderer still exists at
`wear-app/src/main/java/com/reddoor3/forexdial/wear/ForexDialWatchFaceService.kt` for
reference but is no longer registered in any manifest. It can be deleted.

**Watch Face Studio (WFS) is NOT Watch Face Format (WFF).** WFS is Samsung's GUI tool and
has real limits (no conditions, no SMALL_IMAGE in circle slots). Hand-written WFF XML
supports `<Condition>` / `<Expressions>` / `<Expression>` / `<Compare>` / `<Default>`
since Wear OS 4. Dynamic colours driven by battery percent or complication values ARE
achievable. Do not repeat the "WFS can't do conditions, therefore this is impossible"
conclusion - it does not apply to hand-written WFF.

## 3. THE FOUR-FILE RULE (this cost an entire session)

`res/raw/watchface.xml` **alone is not enough.** A WFF module needs all four:

| File | Purpose |
|---|---|
| `res/raw/watchface.xml` | The face content itself |
| `res/xml/watch_face.xml` | Just `<wallpaper/>` |
| `res/xml/watch_face_info.xml` | Declares the preview drawable |
| `res/xml/watch_face_shapes.xml` | **Points at the raw file.** The critical one. |

Plus `res/drawable-nodpi/preview.png` and `preview_circular.png`.

Without the `res/xml/` trio, the face installs, Samsung logs `dwf watchface Info`, and
Google's resolver silently refuses it with:

```
WearServices: [DeclarativeWatchFaceResolver] Declarative watch face in package
  com.reddoor3.forexdial.face could not be parsed - Resource ID #0x0
```

That message is a **reference** failure, not a parse failure, despite the wording.

`watch_face_shapes.xml` content:
```xml
<WatchFaces>
    <WatchFace file="@raw/watchface" width="450" height="450" shape="CIRCLE"/>
</WatchFaces>
```
`width`/`height` MUST match the `<WatchFace>` element in `res/raw/watchface.xml`.

`watch_face_info.xml` attributes are **NOT namespaced** - plain `value=`, not
`android:value=`.

### Ruled out by direct test - all irrelevant
- `classes.dex` in the bundle (AGP injects one even with zero dependencies; harmless)
- Format version (1, 2, 3, 4, 5 all behaved identically)
- Canvas size (450 vs 480)
- XML declaration and comments in the raw file

### How it was found
`adb pull` the WFS-built face already working on the watch
(`com.watchfacestudio.md307digital`), then `aapt2 dump resources` and
`aapt2 dump xmltree` on both APKs and diff the resource tables.
**When a sideloaded thing won't appear, diff against a working artifact on the same
device before touching your own build.**

## UPDATE 2026-07-30: polling speed, Sync Now, tap-to-refresh, layout tuning

**Polling: 15min -> 3min self-chaining.** WorkManager enforces a hard 15-minute floor
on `PeriodicWorkRequest` (confirmed against Android's own docs - not configurable).
`ForexSyncWorker` now re-enqueues itself as a fresh `OneTimeWorkRequest` with a
3-minute delay inside a `finally` block (`CHAIN_WORK_NAME` unique work, `REPLACE`
policy prevents duplicate chains). 3 min = 480 Twelve Data requests/day against the
800/day free cap. `ForexDialApplication.kt`/`BootReceiver.kt` no longer schedule
`ForexSyncWorker` as periodic - the existing one-time kickoff enqueue starts the chain.
Verified naturally (not forced): `sync_started_ts` advanced by exactly 181s between
two checks with zero manual job-forcing.

**Sync Now was slow because it used plain (non-expedited) WorkManager.** Fixed with
`setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)` - Android's actual
mechanism for "user tapped a button, run this now" (WorkManager 2.7+). Measured:
tap-to-completion dropped to 2.7 seconds.

**Tap-to-refresh built and verified end-to-end.** Previously NO complication anywhere
had a `TapAction` set (confirmed by grep) - tapping did literally nothing. Now:
- Watch: `RefreshRequestReceiver` (new), triggered by tapping EUR/USD or the top row.
  Sends a `MessageClient` message to the phone, waits 4s, then force-requests updates
  on every forex complication so the UI refreshes without waiting for the next cycle.
- Phone: `RefreshRequestListenerService` (new, `WearableListenerService`) receives the
  message at `/forexdial/request_sync` and runs the same expedited sync as Sync Now.
- Verified twice: one run hit a genuine transient Twelve Data failure (BTC succeeded,
  EUR/USD+DXY didn't) and self-healed gracefully - EUR/USD's own complication kept its
  last good value rather than blanking (returning null preserves prior state), though
  TopRow's DXY value did go momentarily blank (its null-check only fires when BOTH
  dxy and btc are 0, so a lone DXY failure renders as a blank number, not a full
  fallback). Second tap: clean success end to end in ~2s.

**Layout tuning this round:** yield to 4dp, BTC to full 5-digit price (no "k"), both
repositioned (asymmetric spacing allowed per Ambar - "doesn't have to be symmetrical").
BTC's position is computed live from `Paint.measureText()` on both yield's and BTC's
actual strings each render, shifted left by 25% of the real gap - applied twice now
(two sequential passes of the same formula, not a doubled coefficient). Session dials:
OP/PR/CL text removed (dial fill colour already carries that state), exchange name
doubled, time grown, XETRA sized down slightly from the other two (its 5 letters were
wider and poked outside the circle at the shared size).

**Yield spread formula, now documented (was previously undocumented):**
Germany's FRED 10yr yield (`IRLTLT01DEM156N`) minus the US 10yr (`IRLTLT01USM156N`).
**These are MONTHLY series, not daily** - confirmed by pulling the raw FRED CSV
directly: the June 2026 figures (DE 2.97, US 4.47) give exactly -1.50, matching the
watch. Won't change again until FRED publishes July's figure (~mid-August). Ambar

**Pips bar timeframe, now confirmed (was previously assumed):** Twelve Data's

## UPDATE 2026-08-05: alerts, flashing, yield rework, key architecture, distribution

Long session. Everything below is verified on-device unless stated otherwise.

### Price alerts (B.4) — DONE, verified on a real market crossing
- Phone: set a level in MainActivity. Fires on **CROSSING** the level, not on
  being past it — otherwise it re-fires every sync for as long as price stays
  beyond the threshold. Crossings are evaluated only against a genuinely fresh
  quote, never the preserved-cache fallback, so a failed fetch can't invent one.
- **The alert is keyed by the crossing's TIMESTAMP, not a boolean.** The watch
  dismisses locally by storing "already saw alert `<ts>`". The phone keeps
  re-sending the same fired alert forever (it never learns about the dismissal)
  and it correctly stays hidden; a later crossing carries a new ts and shows as
  new. No phone round-trip to clear. Do not "simplify" this to a flag.
- Watch: transparent bitmap when no alert is live; tap to dismiss
  (`AlertDismissReceiver`); double-buzz once per new ts, not per sync.
- Alert complication polls at **60s** (not 300s) and is in the tap-refresh
  list — the data-change push is unreliable on this device, so the poll is the
  real floor on how late an alert can surface. Without this it took ~3 min.

### Flashing (B.3) — DONE
- WFF **can** animate. `Condition`/`Compare` re-evaluates every second.
- **The live variable is `[SECOND]`, NOT `[SECOND_Z]`.** `[SECOND_Z]` silently
  never fires — no error, condition just reads false forever. This cost several
  debug cycles and looked exactly like "WFF can't animate."
- `%` modulo IS valid, so `[SECOND] % 2` gives a real 1 Hz blink.
- `PartImage` **does** nest inside `Condition` (an earlier conclusion that it
  didn't was wrong — that test had used `[SECOND_Z]`).
- Ambient variant added but **never verified** — the watch has no dim/AOD mode
  and stays `mWakefulness=Awake` on ADB, so ambient can't be triggered.

### Yield — reworked twice
- Now the **daily 2-year EUR−US spread**: US from FRED `DGS2`, EUR from the ECB
  Data Portal AAA euro-area curve. **Both keyless.**
- The old OECD series were **monthly and were running 2 months stale** (on
  2026-08-05 they still served June 1 values). Freshness was the bigger problem
  than the tenor.
- Displayed as a **number at 4dp**, coloured by **day-over-day change**: spread
  rose = cyan, fell = orange. This is a *different meaning* from the old
  LONG/SHORT word, which described the level.
- **Yesterday's value must come from the previous COMMON trading day.** The two
  sources lag differently; pairing newest-with-newest spans two dates and was
  measured 4bp off — enough to fake a day's move.
- Polled **twice daily at 02:00 and 14:00 PT** (was every 15 min). Self-chaining
  to an absolute clock time, not `PeriodicWorkRequest`. DST verified on the JVM.

### Layout
- EUR/USD: two boxes, both sized from **measured text bounds** each render, not
  fixed rectangles. `getTextBounds()` ignores `Paint.textAlign` — pairing it
  with CENTER alignment throws the box off; derive the left-aligned draw x from
  `measureText` first.
- Battery candle moved to (48,215) — the widened rate box collided with it.
- Alert icon at (358,215) 44×129, mirroring the battery.
- **No emoji anywhere.** Tried bull/bear/fire/ice; glyph sizes render
  unpredictably and 🐂 is the OX emoji and reads as a cow. Hand-drawn bell +
  arrow instead, full control.

- **Google Play is impractical here**: personal accounts created after

- **Three packages is a platform constraint, settled 2026-08-05.** WFF requires

### Key architecture
- Keys in `local.properties` → `BuildConfig` → `api/ApiKeys.kt`. Both default
  `""`. **Verified** by building with keys absent: builds fine, bakes in `""`,
  and the phone shows a setup hint naming the missing services.
- **A key cannot be hidden in a client app.** R8 doesn't encrypt strings, NDK

- Yield is deliberately exempt from key checks (ECB/FRED need none), so it

## UPDATE 2026-08-12: buzz-until-dismissed, two alert levels, PUBLISHED

**Published:** github.com/AMBARCAPOOR/ForexDial — MIT, source-only, no APKs.
Verified a clean clone builds all three APKs with NO key baked in.

**Alert vibration took three attempts. Read this before touching it:**
1. Buzz from the DataItem PUSH path — unreliable here, so it never ran at
   all. That was the original "doesn't vibrate" bug.
2. Repeat from the complication POLLING path — the alert complication's 60s
   period is NOT a heartbeat. Measured: 7 calls in 3 minutes, clustered and
   irregular. The system only polls complications while the face is being
   rendered, so screen-off means silence.
3. AlarmManager — rejected on evidence, not taste: SCHEDULE_EXACT_ALARM is
   denied by default at API 36 / targetSdk 35, degrading to an inexact alarm
   Doze throttles to ~9 minutes.
4. **Foreground service** — owns its timer, Doze-exempt while running. Now
   buzzes every 5s for 5 minutes (60 ticks) or until dismissed.

**CRITICAL — this nearly shipped broken.** Starting a foreground service
from the background is DENIED without a battery-optimisation exemption
(`ForegroundServiceStartNotAllowedException`, `code:DENIED`). It worked here
only because this watch had been Doze-allowlisted during earlier debugging.
Caught by REMOVING the allowlist entry and retesting. Two fixes:
`DataLayerHelper` now buzzes directly BEFORE attempting the service, so an
unexempted install degrades to a single buzz rather than silence; and the
README documents the exemption as a requirement.

**Two alert levels**, stored as a comma-separated LIST (`alert_levels`),
deliberately not named upper/lower fields — going to N is then a UI change
rather than a rewrite of storage, payload and detection. Each level is
watched in BOTH directions. When one 3-minute step gaps through several,
the level NEAREST the current price is reported (most recent break, still
the relevant reference). The first cut used the opposite rule — a JVM test
caught it, because the expectation had been written the other way round
minutes after writing the rule.

**Intermittent "EUR/USD failed, DXY failed"** during heavy manual syncing is
Twelve Data's PER-MINUTE rate limit, NOT the per-symbol daily credit
exhaustion behind the August outage. Clears after ~60s. Diagnosing it
required prefs archaeology because the API clients swallow exceptions
without logging — candidate cleanup.

**Wireless ADB:** the watch's pairing drops whenever it leaves the charger.
The PORT usually stays the same; it's the pairing that's lost, so `adb pair`
with a fresh 6-digit code is the fix, not hunting a new port. `adb mdns
services` reveals the current port without reading it off the watch.
